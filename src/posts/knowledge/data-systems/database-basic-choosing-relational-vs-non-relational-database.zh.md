## 概览

> 我会先看应用的需求：数据结构、查询模式和一致性要求。
>
> - **关系型数据库**，比如 PostgreSQL：需要 **join、约束或事务（[ACID](/posts/transactions-and-acid/zh/)）** 的时候。比如在网购系统里，创建订单和扣减库存必须一起完成，所以关系型数据库是很好的选择。
> - **非关系型数据库**：**某一种访问模式占绝对主导**，或者它的数据模型更贴合业务的时候。比如文档数据库适合字段不固定的商品信息，键值存储适合快速的缓存查询，Cassandra 这样的宽列存储适合大规模的聊天消息。
>
> 我还会考虑**扩展性**、**运维成本**和团队经验。我不会默认 NoSQL 一定更快，也不会默认 SQL 扩展不了。我一般默认选关系型，除非有特定需求让别的数据库更合适。实际上很多系统两种都用：关系型作为数据的唯一可信来源，专用存储负责特定部分。

**某一种访问模式占绝对主导**：针对这份数据的请求几乎都是同一种查询。比如聊天消息几乎都是"追加 + 读最新的"。订单则会被用很多种方式查询，没有哪一种占主导，所以更适合关系型。

## 关系型

带显式 schema 的表，加上一套强制规则的工具：`PRIMARY KEY`、`FOREIGN KEY`、`UNIQUE`、`NOT NULL`、`CHECK`、事务、`JOIN`。

当正确性和灵活查询最重要时选它：
- 多步写入必须一起成功或一起失败（创建订单 → 锁定库存 → 记录支付）
- 数据完整性由数据库保证，而不是靠应用代码
- join、聚合、报表、临时查询
- 查询模式还不确定，或者可能会变

典型场景：订单、支付、库存、账户、预订、权限。

<h3 id="acid">ACID</h3>

**关系型数据库**的每个事务都有 **ACID** 保证：**要么全做，要么全不做**、**规则始终成立**、**并发事务互不干扰**、**提交的数据宕机也不会丢**。详见 [事务与 ACID](/posts/transactions-and-acid/zh/)。

## 非关系型

它不是一种东西，而是一族专用存储，每种都为一种访问模式而生：

| 类型 | 适用场景 | 访问模式 |
|---|---|---|
| 键值（Key-value） | 缓存、session、计数器 | 按 key 取，TTL |
| 文档（Document） | 嵌套或字段不固定的数据（商品目录） | 按 id 或索引字段取 |
| 宽列（Wide-column） | 海量的追加写入 | 分区键 + 时间 |
| 时序（Time-series） | 指标、监控 | 指标 + 时间范围 |
| 图（Graph） | 社交关系、推荐 | 邻居、路径 |
| 搜索引擎 | 全文搜索 | 关键词、过滤、相关性排序 |

当某一种窄而稳定的访问模式占主导时选它（session、浏览量、feed、日志、事件）。很多这类存储允许你用强一致换速度，但这是一个选项，不是必须的：比如 DynamoDB 既有最终一致读，也有强一致读。

**访问模式（access pattern）**：应用读写某份数据的一种具体方式。不只是"读还是写"，而是查询的具体形状。常见的有：

| 访问模式 | 例子 | 适合 |
|---|---|---|
| 按 key 取 | 用 session id 取 session | 键值 |
| 按 id 取一个完整对象 | 取一个商品及其所有字段 | 文档 |
| 按分区追加 + 读最新 | 往频道里加一条消息，读最新 50 条 | 宽列 |
| 按时间范围 | 过去一小时的 CPU 使用率 | 时序 |
| 遍历关系 | 朋友的朋友 | 图 |
| 全文搜索 | 搜"无线耳机" | 搜索引擎 |
| join、过滤、聚合、临时查询 | 上个月各地区的营收 | 关系型 |

## 怎么选

1. 数据会怎么被**查询**？
	- 按 key、按时间范围、用 join、全文搜索，还是图遍历？
	- 只有少数几种固定查询：用为它们专门设计的存储。查询很多或可能会变：用关系型。
2. 每次读都必须读到**最新的写入**吗？
	- 支付和库存必须。它们还需要事务，所以用关系型：单机上两者默认都有。
	- 浏览量、feed、分析数据可以稍微滞后，最终一致就够了。
	- 强一致不是关系型独有的，关系型数据库的读副本也可能返回旧数据。关键在于每次读去了哪里。
3. 写入需要**同时更新多条记录**吗？
	- 需要的话用关系型。事务是它的核心优势。
4. 规模会有多大？
	- 关系型靠索引、读副本、分区和缓存可以扩展得很远。
	- 不要只因为*可能*会增长就换 NoSQL。
5. 记录的**字段各不相同**吗？
	- 灵活的 schema 很方便，但校验会转移到应用代码里，数据质量可能慢慢变差。
6. 团队**运维**得了吗？
	- 备份、监控、迁移、故障处理。团队没法安全运维的数据库就是错误的选择。

## 案例

大多数系统用不止一个数据库：关系型存核心记录，再加上专用存储负责热点路径。

| 系统 | 关系型 | 非关系型 | 原因 |
|---|---|---|---|
| 短链接 | | 键值（DynamoDB）、Redis 缓存 | 只按短码查询，读远多于写 |
| 聊天 | Postgres：用户、频道 | 宽列（Cassandra）：消息 | 消息：追加，然后按频道读最新的 |
| 信息流 | Postgres：用户、关注关系 | Cassandra：帖子。Redis：feed 缓存 | 每个用户的 feed 预先算好，按 key 读取 |
| 电商订单 | Postgres | | 订单、支付、库存需要事务 |
| 支付系统 | Postgres | | 强一致、不能重复扣款、审计记录 |
| 票务 / 酒店预订 | Postgres | | 不能重复预订，对座位或房间加行锁 |
| 商品目录 | Postgres `jsonb` | 或 MongoDB | 商品的字段各不相同 |
| 排行榜 | Postgres：分数历史 | Redis sorted set：实时排名 | 快速更新排名，读前 N 名 |
| 限流器 | | Redis | 带 TTL 的计数器，非常快 |
| 指标监控 | | 时序（Prometheus、InfluxDB） | 按时间范围查询，旧数据过期 |
| 搜索 / 自动补全 | Postgres：可信来源 | Elasticsearch：同步过来的搜索副本 | 全文搜索、模糊匹配、排序 |
| 附近的地点 | Postgres + PostGIS | 或 Redis geo | 按位置半径查询 |
| 文件存储 | Postgres：文件元数据 | S3 存文件（对象存储，不是数据库） | 文件是大块二进制，元数据需要查询 |
| 社交图谱（"你可能认识的人"） | Postgres：用户 | 图（Neo4j）：好友关系 | 多跳的好友遍历 |

## Postgres vs MongoDB

人们说"SQL vs NoSQL"时，通常指的就是这两个。MongoDB 是文档数据库，是 NoSQL 的一种。

*2026-11 核对：PostgreSQL 19，MongoDB 8.3。两者差距在缩小，版本变了要重新核对。*

| | Postgres | MongoDB |
|---|---|---|
| 数据形状 | 表、行、固定 schema | JSON 文档，字段可以不同 |
| 关联数据 | 分开的表，查询时 join | 嵌套在一个文档里，一次读出 |
| 事务 | 强，多表事务是核心能力 | 4.0 起支持多文档事务，4.2 起支持跨分片，但不是主要优势 |
| 灵活字段 | `jsonb`（9.4 起） | 原生支持 |
| 横向扩展 | 读副本、分区。分片需要 Citus 这类扩展 | 内置分片 |

默认选 Postgres。当数据天然是一个整体读写的对象、字段变化很大（商品目录、CMS 内容），或者需要内置的横向分片时，再考虑 MongoDB。
